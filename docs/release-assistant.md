# Release preparation

Copilot actively reads release PRs and linked issues, follows relevant discussion and companion PRs, and inspects code at immutable revisions. It reads release evidence in pages and saves cited findings about the user problem, implementation, outcome and limitations before composing notes. Saved findings survive context compaction. The source range determines what ships; external references provide context only. Its read-only tools use `github.token` with Contents, Issues and Pull requests read permissions, separately from the publishing PAT and Copilot credential. No new Secret is needed for public linked repositories.

Review `research.json` in the run artifacts for the findings and actual queries, evidence, URLs, timestamps, revisions and content hashes. `research-progress.json` records progress while generation runs. Missing required investigation, unread diff pages, unfetched evidence citations or exhausted budgets stop generation. Review the resulting claims and `needsReview` entries; tool activity alone does not prove semantic correctness. The model timeout is 600 seconds. Start a new workflow run after upgrading, because old runs retain their pinned tool version.

The policy and layout separate **Release Changes** (what shipped) from **Upgrade Actions** (what affected users must do). Changes appear first; actions follow a divider and are omitted when unnecessary. Group PRs addressing the same user problem and describe the final shipped behavior. Each change (`summary` plus `impact`) and upgrade action is limited to 30 English words, or 60 CJK units. Generation allows one wording correction, then fails if an item remains too long. Update the tool pin and layout together: a shared policy URL changes editorial rules but does not replace the renderer, local layout or composition prompt.

An auxiliary reference that Copilot requests and receives HTTP 404/410 for is retained in `unavailableReferences`, with a limitation and review flag on the affected findings. Any resulting Changelog entry keeps the review flag; an unavailable URL cannot be cited as evidence. Source PR reads, authentication errors, rate limits and server failures still block generation. Use full GitHub URLs or `owner/repository#number` in cross-repository references to avoid ambiguous bare numbers.

After **Prepare release** succeeds, open the created or updated PR from the link at the top of the Actions run summary. The `prepare` job also exposes this URL as `pull-request-url`. The PR description shows the complete version Changelog, exactly as written to its file, with generation details collapsed below. **Re-run all jobs** replaces both the description and generated files with the latest notes while keeping the same PR link.

Run **Prepare release** with a target branch, explicit version (including prereleases), automatic tag rank or manual starting tag, optional ending ref and a model from the dropdown. Install `RELEASE_ASSISTANT_TOKEN` (App token or fine-grained PAT with Contents and Pull requests write permission) and `COPILOT_GITHUB_TOKEN` (Copilot Requests permission), or configure a compatible model endpoint and `RELEASE_ASSISTANT_API_KEY`.

Leave `from_tag` empty to discover up to three starting tags and use `from_tag_choice`: `latest` (default), `second-latest`, or `third-latest`. Candidates must be reachable from the ending commit and lower than the proposed version; they are sorted by SemVer from highest to lowest, including prereleases. Annotated/lightweight tags and an optional `v` prefix are supported. Non-SemVer, unrelated and later tags are excluded. GitHub's native form cannot dynamically load tag names, so actual candidates and the selected tag/SHA appear in the run summary, PR generation details and snapshot artifact. Selecting a rank without a candidate fails explicitly.

Fill in `from_tag` to override the automatic choice with any existing tag, including one outside the suggestions or a non-SemVer baseline; ancestry checks still apply. The `prepare` job exposes `from-tag`, `from-sha` and JSON `recent-tags` outputs. Selection is frozen before inference for each workflow run. **Re-run all jobs** retains that run's tag, SHA and candidates even if repository tags change. A new **Run workflow** resolves the inputs again and refreshes the range in the same open Release PR. Leave `to_ref` empty to use the target branch's latest HEAD, or specify an explicit cutoff. A publishing run must end at the target HEAD; use preview mode for historical ranges.

The model dropdown defaults to `gpt-6.1-sol`, followed by `gpt-6-astra`, `gemini-4-argon`, `gpt-5.3-codex` and `gemini-3.8-flash`. The selected model overrides `ai.model`; configuration and the layout template are read from the latest main branch on every run, and the selected policy source is resolved again. Model IDs must be enabled for the configured provider/account; generation fails if unavailable, with no automatic fallback. **Re-run all jobs** regenerates the same open PR and replaces generated files, including manual edits, while retaining its original model and source range. To select a different model or refresh a stale range, start a new **Run workflow**; it resolves the range again and reuses the same open PR. Old reruns stop if a newer run has replaced their snapshot. Closed/merged PRs and existing tags cannot be reused.

When a new range is frozen, the tool first commits only the snapshot. An existing Release PR can temporarily fail validation until successful generation commits the notes and manifest. If generation fails, diagnose its run and retry it; do not bypass validation or handcraft missing provenance.

`maxPromptBytes` is 256,000 UTF-8 bytes. For Copilot it bounds the initial research instructions; release evidence is fetched in pages and context compaction respects the model's reported runtime limit. Research budgets and the timeout still apply. For a compatible API provider, the limit continues to cover the complete evidence prompt. Oversized inputs fail explicitly rather than being silently truncated.

The optional advanced `changelog_policy` field at the bottom of the workflow form accepts a repository-relative path or a public HTTPS text/Markdown file URL. GitHub's native form does not support collapsed input groups. Leave the field blank to use `policy` in `release-assistant.yml`; omit that configuration too to use the bundled policy. To share rules centrally, use `https://github.com/hwameistor/release-assistant/blob/main/templates/changelog-policy.md`, either in the form or as the configuration's `policy` value. Every run and rerun fetches the latest file, so editing the shared rules does not require workflow changes. A commit-SHA URL deliberately pins the policy revision. Changing the form's URL requires a new run with otherwise identical release inputs; a native rerun keeps its original input. After first upgrading the workflow/Action for this option, start a new workflow run; rerunning an older run retains its old workflow and pinned tool version.

External files must be directly readable without login, URL credentials, query parameters or redirects. Invalid/HTML/empty responses and files over 128 KiB fail without fallback. GitHub file URLs resolve to a commit before reading. The run artifacts retain the exact policy, source and hash; the run summary and Release PR show the source and resolved revision. Existing committed manifest fields and installed release validators remain compatible. The layout template is still configured separately.

The PR contains the cumulative Changelog, version log, Chart version/appVersion and provenance. Dependency/tool image versions are managed separately. Review included changes, exclusions and uncertain statements, then mark the draft ready. Require **Validate release PR / validate** and an up-to-date branch before merging; install this workflow on each release branch as well.

After review, merging the Chart version update follows the existing publication triggers. The release workflow reads `changelogs/released/<Chart version>/changelog` from the exact checked-out commit through Release Assistant's `release-body` command. It verifies Chart version/appVersion, the release manifest's repository/version/content hash, and any existing version tag's source commit. Missing or empty notes, missing/mismatched provenance, or a version/source mismatch stop publication before Chart Releaser runs. A manually prepared release must also provide the matching version log and manifest; changing only Chart.yaml is no longer sufficient.

CI copies the verified text to the Chart's `RELEASE_NOTES.md` and configures `release-notes-file` in `helm/.cr/config.yaml`. Chart Releaser reads that packaged file as the GitHub Release body when creating the release. The body matches the committed version log; publication does not call AI or reread the latest policy. Generation details from the PR description are not included. The staged file exists only in the CI workspace and resulting Chart package.

Chart, image and CLI binary jobs use the same captured source SHA and Chart version. The existing release creation/asset upload mechanism remains in place. Historical Releases are not rewritten, and Chart Releaser's existing retry behavior is unchanged.

This change connects the release body only. The current Chart Releaser does not apply the tool's `prerelease`/`make-latest` outputs; prerelease labels and latest-version behavior still need a separate publication change. Keep test Release PRs as drafts and do not merge them until an actual release is intended.

This integration does not change the Chart version and does not publish a product release when merged. Configure and test the credentials and generation first. See https://github.com/hwameistor/release-assistant for the specification, tests and CLI usage.
